# Laya — модель быстрых решений (System 1) для валидатора психтерапевта

Справочник по модели, её устройству и **правилам работы с ней**.
Документ собран из карточек моделей на HuggingFace, официальной документации
`laya`, кода библиотеки и независимых замеров. Все утверждения с пометкой
**[док]** взяты из документации авторов, **[замер]** — измерения сторонних
пользователей, **[наш]** — наши собственные прогоны.

## 2. Формат входа — точно

```
[CLS] {тип} question: {instructions} [SEP] [MASK] {вариант0} [MASK] {вариант1} ... [SEP] {state} [SEP]
```

`common.py::build_sequence` **[док]**

- Перед инструкциями **вставляется литеральная строка типа**: `choice question: …`,
  `score question: …` или `noul question: …`.
- Каждый вариант начинается со своего `[MASK]`, дальше текст варианта.
- Варианты разделяются одним `[MASK]`, а не ведущими масками.
- `max_len` (по умолчанию 1024 в конфиге модели) — весь вход.
- `head_max_len` (по умолчанию 256 в конфиге) — **только вопрос и варианты**.
  Остаток уходит под текст пользователя.
- Ответ читается с позиций `[MASK]`, скошен softmax по вариантам этого вопроса.

### 2.1 Жёсткий лимит 48 токенов на один вариант

`common.py:95-99`: каждый вариант режется токенизатором до 48 токенов.
**Молча**, без предупреждения. Если варианты не влезают в `head_max_len`,
каждый режется ещё сильнее: `max(4, (head_max_len - 16) // n_вариантов)`.

**Можно ли увеличить?** Технически — да, это константа в коде библиотеки
(`max_length=48`), и `head_max_len` настраивается. Но делать не надо **[док]**:

- чекпоинт обучен с этим ограничением — это тренировочное распределение,
  выход за него out-of-distribution;
- авторы прямо предупреждают: длинные и похожие подписи «могут дойти до
  модели прочитанными одинаково» — качество падает задолго до обрезки;
- все официальные примеры используют варианты длиной **3–7 слов**.

**Правильный путь — укорачивать текст варианта до <48 токенов.** Проверять
нужно так: измерить длины токенов, как в `tools/laya_probe.py` (мы так делаем).

## 3. Три типа вопросов

| Тип | Ответ | Как считается |
|---|---|---|
| `choice` | один из N вариантов | argmax по вероятностям вариантов |
| `score` | уровень 0..N-1 | среднее взвешенное Σ i·pᵢ (дробное число!) |
| `noul` | да/нет | вероятность **второго** слота, семантический порядок всегда `[false, true]` |

`common.py:12`, `agent.py:653-708` **[док]**

Для `choice` ключи словаря рендерятся **как есть**: `"A: <описание>"`, либо
просто `"A"`, если описание пустое.

## 4. Документированные грабли (главное)

### 4.1 Булевы подписи вариантов перехватывают ответ — issue #156

**Самое важное для нас.** Измеренный баг: при подписях `true`/`false` или
`yes`/`no` модель отвечает **по токену подписи**, игнорируя описание.

| подписи вариантов | положительный текст | отрицательный текст |
|---|---|---|
| `positive` / `negative` | ✅ | ✅ |
| `true` / `false` | ❌ выбрал `false` | — |
| `yes` / `no` | ❌ выбрал `no` | — |
| `A` / `B` | ✅ | ✅ |
| `1` / `2` | ✅ | ✅ |

Автор: *«The model appears to answer from the label token»*. Официальный совет
из README: **«Avoid boolean-word labels in `choice` questions. Choice keys are
rendered verbatim, and the current checkpoints can follow labels such as
`true`/`false` or `yes`/`no` instead of the option descriptions.»**

Дополнение из документации: *«Semantic `choice` labels do not make negation
safe»* — то есть даже семантические подписи не спасают отговорки.

**Для `noul` есть штатное решение:** нейтрализовать подписи, сохранив смысл:
```python
{"type": "noul", "instructions": "...",
 "criteria": {"true": "да, ...", "false": "нет, ..."},
 "labels": {"true": "A", "false": "B"}}
```

### 4.2 Порядок вариантов меняет ответ

*Замер:* 305 решений, 5 перестановок вариантов — **1 из 5 ответов меняется
только от перестановки**; устойчивость падает с ростом числа вариантов
(2 варианта 100%, 4 — 82%, 6 — 72%, 12 — **0%**) **[замер]**.
Другой замер: разворот вариантов изменил 69 из 100 ответов **[замер]**.

Документация: *«Option order can change a `choice` answer… fix your option
order and treat it as part of the schema. Changing the order of a dict literal
in your code is a silent behaviour change.»*

**Следствие для нас:** порядок словаря `criteria` — часть схемы, а не
косметика. Обязательна проверка перестановкой: если ответ не изменился —
подписи/текст не управляют выбором.

### 4.3 `score` у мультиязычного чекпоинта сломан по позиции

*«it rarely picks the first-listed level, in any language, including English
(0 of 290 in one independent run)»* **[док/замер]**. Вывод авторов: для
английских `score` использовать английский чекпоинт, для остальных —
**проверять на своих данных**. Мы `score` не используем.

### 4.4 `noul` с богатыми критериями ухудшается

Абляция авторов на коротких китайских командах **[док]**:

| вариант | точность | средняя уверенность |
|---|---|---|
| `noul` без критериев | **0.6667** | 0.813 |
| `noul` с критериями | 0.4583 | 0.892 |
| `noul` с описанием сценария | 0.4722 | — |
| `noul` с JSON-состоянием | 0.4167 (= константа «всегда true») | — |

Вывод: *«The documented guidance does not make the `noul` path read the
language differently; it makes the questions stop discriminating.»*

Для `choice` те же правки **помогали** (0.722 → 0.778) **[док]**.

### 4.5 Модель — матчер тем и регистра, а не смысловой судья

Крупнейший независимый замер (100 сценариев, 305 решений) **[замер]**:

| тип | n | Laya | константа «читать не текст вовсе» |
|---|---|---|---|
| `choice` | 89 | 48.3% | 38.2% (+10.1) |
| `noul` | 144 | 47.2% | 72.9% (**−25.7**) |
| `score` | 72 | 16.7% | 31.9% (−15.3) |

Вывод автора замера: *«The routing head works. The boolean and ordinal heads
do not.»* Что работает: *«Laya is good at topic-shaped questions. When the
right answer correlates with which words are present, it lands.»*
Что не работает: отрицания, отозванные утверждения, арифметика, длинные
тексты, смена регистра (urgency читалась по тону, а не по смыслу), чтение
только первой фразы.

Отсюда наше правило: **критерии формулируются через конкретные, наблюдаемые
слова юзера, а не через абстрактные определения.**

### 4.6 Базовая модель не откалибрована

`rl_agent_config.json` базовой модели: `temperature: [1.0, 1.0, 1.0]`,
`temperature_by_options: {}` **[док]**. Карточка модели: *«Ships uncalibrated.
It is systematically over-confident (mean confidence 0.75–0.83 against much
lower accuracy). Refitting one temperature per (question type, option count) on
held-out data moves mean ECE 0.314 → 0.106.»*

У `alfred361` варианта температуры подогнаны (`[1.036, 0.980, 0.994]`), но это
подгонка на английских данных.

#### Грабли приёма вендорских цифр **[замер]**

Автор модели обнаружил, что его собственная таблица по 51 языку не
воспроизводится: три машины, три версии библиотеки, CPU и MPS дают один и тот же
результат, не совпадающий с закоммиченным файлом (issue #208, §1.1). Чекпоинт
при этом не менялся. **Отсюда правило: цифра из карточки — это гипотеза, а не
факт, пока не проверена на наших данных.**

Два конкретных следствия для калибровки:

- `macro ECE 0.7331 → 0.5709` — **не** улучшение модели, а правка клампа
  температур в `[0.5, 5]` (issue #42). Argmax у temperature-scaled softmax
  инвариантен при любой положительной температуре, поэтому accuracy при этом
  физически не может измениться. Автор это оговаривает прямо: *«Accuracy
  columns are unaffected»*.
- Штатного клампа может **не хватить** для неанглийских бинарных суждений. На
  `zh-decision-bench` refit для `noul:2` даёт сырую температуру **T = 10.23**,
  что превышает `TEMP_MAX = 5.00`; тест ECE при этом 0.180 → 0.098. Автор:
  *«Chinese binary-judgment over-confidence outruns the shipped clamp's
  correction range»* **[док]**. У нас ровно этот случай — русские бинарные
  `noul`-вопросы, — значит при калибровке нельзя молча упереться в кламп, нужен
  isotonic/Platt-фит.

### 4.7 Уверенность: две разные метрики, путать нельзя

`common.py:273-299` **[док]**

| поле | что это | откалибровано? |
|---|---|---|
| `answer_confidence` | `max(вероятности)` = вероятность выбранного ответа | **да** |
| `confidence` (choice/score) | `1 − энтропия/log(вариантов)` | **нет** |
| `confidence` (noul) | `max(p_true, 1−p_true)` = то же, что `answer_confidence` | да |
| `action.act_probability` | всегда ≈1.0, сигнала не несёт (issue #185) | нет |

Документация дословно: *«the two must not be compared against the same
threshold»*. **Маршрутизацию делаем по `answer_confidence`.**

Порог — политика приложения, а не свойство модели:
*«A threshold is a policy you choose from measured accuracy at that coverage on
your data, not a property of the model.»*

#### Но и `answer_confidence` сепарирует плохо **[замер]**

Независимые замеры сообщества:

| замер | что показано |
|---|---|
| issue #450 (741 размеченных запроса, RTX 2000 Ada) | ECE: Jev 0.049 · laya 0.322 · typed 0.422 · multi 0.253. Автор: *«This looks like a calibration offset on the `noul` head rather than a comprehension failure: the ranking is not random, the midpoint is.»* Точность не пересекает границу Уилсона ни на одной глубине отбора |
| discussion #13 (100 сценариев, 305 решений) | разделение правильных/неправильных по confidence = **0.086** (0.757 против 0.671); **54% ответов с confidence ≥ 0.90 были неправильными**. Вывод автора: *«a confidence threshold cannot be used to route between auto-handle and human review»* |
| routing-задача самого автора (180 запросов, zero-shot) | наоборот, **недобор** уверенности: среднее P(выбранного) ниже точности на −0.18…−0.19 |

**Вывод для нас:** направление перекоса зависит от задачи (где-то переоценение,
где-то недооценение), поэтому единственный способ узнать — откалибровать на
своих данных. Порог по `answer_confidence` нельзя ни переносить из документации,
ни выбирать «на глаз».

### 4.8 Длинные тексты

До ~4000 токенов — 16-18 из 20 верно; дальше 8-17 из 20 **[док]**. Есть
режим `max_len=8192` (в конфиге по умолчанию 1024). Короткие тексты от этого
не меняются.

### 4.9 Число вариантов

До ~20 вариантов в `choice` **[док]**. Мы используем 2 — с запасом.

### 4.10 Зависание `laya.load()` при установленном TensorFlow

Если в окружении установлен TensorFlow, `transformers` опрашивает его рантайм,
и abseil может уйти в дедлок при сборке модели **[док]**.
Решение: запускать скрипт с переменной окружения `USE_TF=0`.

## 5. Официальный стиль вопросов

Примеры из `laya/presets.py` — образцы, которые рекомендует сама библиотека
**[док]**:

```python
"is_urgent":  {"type": "noul", "instructions": "Does `message` communicate time pressure or a deadline?"},
"refund_requested": {"type": "noul", "instructions": "Does the customer ask for money back?"},
"is_phishing": {"type": "noul", "instructions": "Is this email a phishing or scam attempt to steal money, credentials, or personal data?",
                "criteria": {"true": "phishing, scam, or fraud", "false": "a legitimate email"}},
"intent": {"type": "choice", "instructions": "What does the customer want in `message`?",
           "criteria": {"refund": "money returned or a duplicate charge reversed",
                        "technical_help": "a bug, outage or integration problem",
                        "other": "none of the other options fits"}},
```

Что видно из примеров:
- инструкция — короткий вопрос в одну клаузу, в настоящем времени;
- варианты — **3–7 слов**;
- подписи семантические, **не булевы**;
- у `choice` есть «ловушка» `other / none of the options fits`;
- состояние в примерах — словарь, и поле упоминается в инструкции в
  обратных кавычках: `` `message` ``.

Официальный совет на случай слабых ответов **[док]**:
*«If `noul` answers look weak, the same question as a two-option `choice` with
neutral keys (`A` / `B`) and yes/no descriptions is a useful check.»*

а из-за плохо поставленного вопроса. Но проверяется это только прогоном стенда,

## 8. Правила работы с моделью в нашем проекте

1. **Никаких булевых подписей.** Подписи вариантов: `A`/`B` (или семантические),
   смысл переносится в код стенда. Булевы подписи — запрещены (§4.1, §6.2).
2. **Усредняем ответ по двум перестановкам вариантов.** Одиночный прогод
   недостоверен: перестановка переворачивает до 6 из 9 ответов (§6.2).
   Порог по уверенности — только по `answer_conf` усреднённой вероятности.
3. **Рабочий тип вопроса — `noul` с `labels: {true: A, false: B}`.** Даёт 15/18
   против 14/18 у `choice` с нейтральными подписями (§6.1).
4. **Длинные описания вариантов оставляем.** Короткие (3–7 слов, как в
   примерах авторов) дали 9/18 — хуже. Тихая обрезка на 48 токенах есть, но
   она не была главной проблемой (§6.2).
5. **Критерий через конкретные слова юзера, а не через абстрактное
   определение.** Элемент, который нельзя описать наблюдаемыми признаками,
   для этой модели негоден — отправлять в LLM-валидатор.
6. **Уверенность — только `answer_confidence`.** Порог — наша политика,
   подбирается на данных, а не переносится из чужой документации. Проверено:
   без калибровки уверенность плохо сепарирует верные ответы (§4.7).
7. Любое изменение критериев проверяется **прогоном `tools/laya_probe.py` на
   всех кейсах `cases.yaml` сразу**: правка в
   `element_validation_rules*.yaml` без прогона уходит в продакшн-валидатор
   незамеченной. Регрессия на одном элементе видна только в сравнении.
8. Модель — `convaiinnovations/laya-multilingual`, ревизия `e4e9ddf`. Проверено:
   alfred361 хуже на русском (§6.4).
9. `e3` был системным промахом на старых критериях и закрылся правкой
   формулировки, а не дообучением (§6.3). Значит любой «известный промах» сначала
   проверяется переформулировкой вопроса, и только потом — маршрутом в
   LLM-валидатор.

## 9. Куда двигаться дальше

**18/18 на двух кейсах — это не потолок, а отсутствие данных.** Модель выросла
с 9/18 до 18/18 не потому, что стала умнее, а потому, что мы перестали с ней
спорить нечестно: переформулировали вопросы. Собственные цифры вендора на том
же принципе типизированных решений: `laya-multilingual` zero-shot = **0.352 при
majority-class baseline 0.461** (то есть хуже константы), а 0.766 в карточке
принадлежит дообученному `laya-typed-decisions` на его же тренировочном сплите
**[док]**. У нас в `cases.yaml` два кейса — этого недостаточно, чтобы утверждать
что угодно.

Что дальше, по убыванию реалистичности:

1. **Набирать кейсы** — единственное, что реально двигает оценку. Эталон
   берётся из Gemma-прогона, лежит в `validation<N>.json`; сейчас заполнено 2
   кейса из ~13, что уже есть в `test_cases/new_tests_for_validator/`. Каждый
   новый кейс — это и есть работа, всё остальное следствие.
2. **Калибровка температур** по типам вопросов: авторы показывают переход
   ECE 0.314 → 0.106 **[док]**, сейчас модель не откалибрована никак
   (`temperature = [1,1,1]`). С оговоркой §4.6: для бинарных `noul` сырой фит
   может превысить `TEMP_MAX = 5.00` (у авторов на китайском получилось 10.23),
   поэтому нужен isotonic/Platt-фит, а не только перебор T. Пункт особенно важен
   потому, что без него маршрутизация по `answer_confidence` вообще не работает
   (§4.7).
3. **Дообучение под наш воркфлоу** — единственный путь к настоящей способности.
   Карточка модели прямо говорит: *«Fine-tune for a specific workflow; that is
   where the capability comes from»* **[док]**. Нужны десятки–сотни размеченных
   кейсов; рецепт опубликован в репозитории модели. Прагматично: сначала пункты
   1 и 2, потому что дообучение без своей разметки и калибровки бессмысленно.
4. **Дальнейшая подгонка формулировок под 2 кейса** больше невозможна в любую
   сторону: 18/18 нечем улучшать, а проверять честность не на чем. Это и есть
   причина, по которой пункт 1 — первый.

## 11. Правила препроцессинга входных данных для Laya (System-1)

Модель Laya (mmBERT 322M) не выполняет глубокого смыслового рассуждения.
Она считывает поверхностные лексические и синтаксические маркеры.
Поэтому перед подачей текст пациента должен пройти нормализацию по следующим правилам:

### 11.1 Фильтрация сюжетного экшена в сновидениях (Анти-боевик)
* **Проблема:** Если пациент рассказывает сон с динамичным внешним сюжетом («демон напал», «схватил ребенка», «ударил молотком», «выстрелил»), Laya приписывает эти действия реальному поведению человека (`e2=true`) или видит границы (`e5=true`).
* **Правило:** Сны перед подачей в System-1 должны быть очищены от голливудского экшена. В тексте должно оставаться только **субъективное переживание аффекта** («снился кошмар о беззащитности перед внешней угрозой, чувствовал бессилие отстоять границы»). Если пациенту важен именно детальный сюжет сна — такой запрос эскалируется напрямую в LLM (System-2).

### 11.2 Очистка от мета-разметки самоанализа
* **Проблема:** Заголовки вроде `Корневой страх:`, `Психосоматика:`, `Тип 4` искажают распределение внимания модели. Слово «страх» в заголовке дает ложноположительный триггер на `e7` (Эмоции), даже если в жалобе нет живого эмоционального процесса.
* **Правило:** Запрещены любые служебные теги и названия эннеатипов. Мысли клиента о страхах должны подаваться естественной речью первого лица: «В глубине я боюсь, что...».

### 11.3 Защита от ложных правил (`e5`) в конструкциях «Если ... То»
* **Проблема:** Наличие слова «условие» в критериях в сочетании с фразами вида «Если я не сделаю X, заболит Y» воспринимается моделью как категорический императив (`e5=true`).
* **Правило:** Причинно-следственные связи должны формулироваться как констатация фактического опыта без сослагательного наклонения и псевдо-предписаний.

### 11.4 Изоляция соматического контекста — **ГИПОТЕЗА НЕ ПОДТВЕРДИЛАСЬ, см. §13**
* **Гипотеза (была записана как правило):** Насыщенное анатомическое описание (перечисление мышц, суставов, органов) «зашумляет» скрытые психологические маркеры.
* **Измерено 02.10.2026 (§13):** соматика вырезана из 4 кейсов — **все 108 вердиктов совпали с исходными, до единого**, точность 85/108 в обоих вариантах. Ни один элемент не сдвинулся.
* **Что остаётся в силе:** если запрос **чисто** телесный, он классифицируется как Negative Control (все `false`). Это правило про другой случай, сплит-тест его не проверял.

### Принцип описания феноменов речи (взамен словарного хардкода)

Запрещён пословный хардкод токенов (перечисление слов в кавычках или скобках) — сужает границы класса, провоцирует ложные срабатывания по случайным совпадениям и не обобщается. **Примеры нарушений, найденные в критериях 02.10.2026:** `(«должен», «обязан»)` в вопросе `e5`, список эмоций `(страх, вина, стыд, гнев, тревога)` в `e7`, дословное «теряет ощущение себя» из кейса task11 в `e4`.

Рекомендуется функциональное описание речевого акта — формулировка того, что именно говорящий делает в речи (наделяет внешний объект спасительной силой, приписывает себе статус неполноценности, описывает пусковой эпизод, накладывает категорический запрет).

**Академический жаргон — правило удалено как неподтверждённое.** Раньше здесь стоял запрет на термины вроде «негативная Я-концепция», «дефектность Я», «суррогатная потребность» с обоснованием «в жалобах клиентов таких слов нет, векторные пространства не сходятся». Измерение на `e4` (§13) этого не подтвердило: **с жаргоном — 5 ошибок, с заменой полюсов на обычные слова — 6 ошибок**, и модель во втором случае перестала различать тексты (`true` на 10 из 12 кейсов). Жаргон в критериях удерживает элемент в рабочем состоянии; измеренного вреда от него нет.

**Итог по вычистке формулировок:** функциональное описание речевого акта даёт выигрыш не всегда, а зависит от элемента (`e6` 5→2 ошибки, `e5` 7→5, `e8` 1→0; `e4` 5→5 с вырождением сигнала). **Правка пакетами противопоказана:** все девять сразу дали 80→76 из 108. Правило — один элемент, один прогон, сверка счёта по этому элементу.




### 4.11 Ловушка зеркального отрицания («нет X» в false_criteria) — эмпирически доказано

Попытка сделать критерии бинарно-зеркальными вида:
* `true`: «предельный крах или гибель личности»
* `false`: «нет предельного краха или гибели личности»
приводит к **обвалу точности модели (с 78.7% до 66.7%)**, а на элементе `e3` число ошибок выросло с 1 до 7 из 12.

**Причина:** Энкодер mmBERT (322M) — это матчер распределения токенов в эмбеддингах. 
Во фразах «X» и «нет X» 90% токенов **абсолютно идентичны**. Частица «нет» — это всего один субтокен, который не способен развернуть 768-мерный вектор предложения в противоположную сторону. Для модели оба варианта значат одно и то же — тему X. При наличии в тексте любых смежных слов оба слота активируются одинаково, и модель сваливается в случайное угадывание.

**Железное правило:** `false_criteria` **ЗАПРЕЩЕНО** формулировать через отрицание токенов из `true` («нет X», «отсутствие X», «без X»). 
Вариант `false` обязан быть **самостоятельным альтернативным смысловым полюсом** с совершенно другим набором слов:
* Правильно для e3: `true`: «непереносимое крушение жизни» vs `false`: «текущая эмоциональная реакция на проблему».
* Правильно для e5: `true`: «категорическое правило, жесткий запрет» vs `false`: «мягкое пожелание, совет или причинно-следственные связи».

### 4.12 Ловушка «нейтральных фактов и нормы» в false_criteria

Попытка использовать в `false_criteria` формулировки вроде *«нейтральные обстоятельства, обычные события или норма»* взамен соматических маркеров **обваливает модель (до 71.3%)** и вызывает шквал ложноположительных срабатываний на `e4` (6 ошибок из 12) и `e1` (5 ошибок).

**Причина:** Клиент в психотерапии **никогда не пишет о «норме и нейтральных событиях»**. Текст пациента всегда заряжен болью, страхом, тревогой или дискомфортом. 
Когда Laya видит, что `false_criteria` требует «нейтральных фактов», а в тексте идёт речь об аде и страдании, энкодер мгновенно отбрасывает `false` как несоответствующий тональности текста и принудительно выбирает `true`.

**Железное правило:** Отрицательный полюс не должен описывать «здоровую норму» или «нейтральность». Он должен описывать **другой, непатологический вид того же эмоционального напряжения** (например: «ситуативное бессилие или страх без самоуничижения», «локальные трудности без распада»).

## 13. Три проверки гипотез, которые дали неожиданные ответы

### 13.1 Академический жаргон в критериях: вреда не измерено, есть данные за его сохранение

Раньше §11 требовал не использовать клинические термины («негативная Я-концепция»,
«дефектность Я», «суррогатная потребность») на том основании, что «в жалобах клиентов
таких слов нет, векторные пространства не сходятся». **Это было утверждение без замера.**

A/B на `e4`, всё остальное (критерии, кейсы, режим) идентично:

| Вариант `e4` | Ошибок | Поведение модели |
|---|---|---|
| с академизмом: «прямая качественная оценка дефектности или неполноценности своего Я» | **5** | живой сигнал: ловит все 5 позитивных кейсов, ошибается на 5 отрицательных |
| без академизма: «прямая оценка себя как плохого или недостаточного» | 6 | `true` на **10 из 12** — различать перестала |
| полностью функциональный (речевой акт, без жаргона и в вопросе) | 5 | `false` на **12 из 12** — сигнал выродился в константу |

**Вывод:** замена жаргона обычными словами ухудшила элемент. Академизм в `e4` оставлен,
запрет из §11 удалён как неподтверждённый. Методологический вывод шире: §11 содержала
утверждения без цифр, и соседние её разделы уже опровергались нашими же прогонами
(§4.4, §6.1) — документу нужна пометка «измерено/не измерено» у каждого правила.

### 13.2 Соматика в кейсах: **сплит-тест дал нулевой эффект**

Гипотеза: анатомическое перечисление «зашумляет» психологические маркеры, и без него
модель работает лучше. Проверка — `tools/somatic_ablation.py`: тот же файл критериев,
тот же режим, из 4 кейсов вырезано 8 телесных фрагментов (task3, task6, task8, task10),
эталоны скопированы и проверены на идентичность.

| | С соматикой | Без соматики |
|---|---|---|
| Общий счёт | 85/108 | **85/108** |
| Ошибки по элементам | e1=3 e2=4 e3=2 e4=5 e5=5 e6=1 e7=0 e8=0 e9=3 | **идентично** |
| Приоритетные | 42/48 | **42/48** |

**Все 108 вердиктов совпали до единого.** Ни один элемент, ни один кейс не сдвинулся.

**Вывод:** соматика в тексте пациента **не влияет** на вердикты Laya. Вход чистить
не требуется ради точности; §11.4 и протокол «хирургического вырезания» помечены

### 13.3 Правка критериев пакетами противопоказана

Первый же заход — переписать все девять элементов разом — дал **63/108** против 81/108
базы. Причина в том, что элементы тянут в разные стороны: усиление `true`-полюса `e3`
подняло сразу все кейсы (`task6` 0.440 → 0.712), и выигрыш на `task11` (0.447 → 0.915)
перекрылся ростом ложноположительных. Вопросы Laya независимы (отдельная строка батча
на элемент), поэтому элементы можно чинить по одному — но только по одному.

| Элемент | Ошибок до | после | Вердикт |
|---|---|---|---|
| `e6` | 5 | **2 → 1** | выигрыш |
| `e5` | 7 | **5** | выигрыш |
| `e8` | 1 | **0** | выигрыш (уже был функциональным) |
| `e1` | 5 | **3** | выигрыш |
| `e3` | 2 | 2 | нейтрально (правка дала `task11` 0.447 → 0.915, но и рост ложноположительных) |
| `e9` | 3 | 3 | нейтрально (ушёл академизм и зеркальное отрицание) |
| `e4` | 5 | 5 | регресс поведения: функциональный вариант даёт константу |

### 13.4 Ловушка, стоившая дороже всего: текст `false_criteria` ловится словами жалобы

`false_criteria` — не «антитеза», а самостоятельное описание. Как только его слова
совпадают со словами пациента, он перетягивает вердикт — даже когда по смыслу
описана противоположная вещь.

| Элемент | Ошибочный полюс | Что он сломал |
|---|---|---|
| `e6` | «общий **фоновый** дискомфорт» | цеплялся к слову «фоном» в жалобах → `e6=false` там, где триггер назван (`task10`, `task11`) |
| `e5` | «**тупик, невозможность** сдвинуться» | в `task1` слова «постоянный тупик» стоят у пациента, а ожидался `e5=true` → вердикт ушёл в `false` (4 ошибки разом) |
| `e6` | «непрерывная тревога, **напряжение** или грусть» | ловило «внутреннее напряжение» → `e6` упал до 9 ошибок из 12 |

Отсюда правило проверки перед каждой правкой полюса: **прогнать изменённый полюс против
текстов кейсов и посмотреть, не содержит ли он слов из жалоб пациента.**

#### 13.4.1 Обратное явление: полюс совпадает с текстом, а модель отвечает `true` (03.10.2026)

Разбор всех 45 ошибок официального прогона (`error_landscape.py --zone 0.10`) показал
явление, **противоположное** описанному выше. В трёх кластерах ложных срабатываний
`false_criteria` заведомо совпадает с текстом пациента — а модель всё равно отвечает `true`:

| элемент | полюс `false` описывает… | модель всё равно | p |
|---|---|---|---|
| `e2` | «внутренние переживания без внешнего проявления» («хочется прилечь») | `true` | 0.743–0.832 |
| `e5` | «причинно-следственная связь, пожелание» (конструкция «Если…то») | `true` | 0.785, 0.859 |
| `e3` | «привычный фоновый дискомфорт» и «констатация дефицита» | `true` | 0.53–0.844 |

Значит перекос 34 FP против 11 FN — это **не «полюс тянет вердикт»** (как в таблице
выше), а «модель не выбирает между полюсами и тянет в `true`» — механизм §16.1.
`e5` подтверждает гипотезу §11.3, которая до сих пор была помечена непроверенной.

**Практическое следствие для правок:** сузить `false_criteria` под слова жалобы
**недостаточно** — эти правки уже делались и дали обратный эффект. Работать надо с
различительным признаком в самом вопросе, а не с составом полюсов.

### 13.5 Потолок честных 100% по приоритетным на этих кейсах

`e6` упирается в противоположные требования к двум кейсам:
- `task10` — ожидается `e6=true`, но в тексте **нет** сценария: только «по утрам нет сил встать, ночью мучает бессонница»;
- `task6` — ожидается `e6=false`, хотя момент «после пробуждения» назван.

Критерий, ловящий время суток, делает оба одновременно верными только если `task10`
и `e6=false` разойдутся. Проверено: добавление «повтор по времени» в `true`-полюс `e6`
подняло `task7` в ошибку (0.501 → 0.456) и **не** помогло `task8` (0.271 → 0.305).

Аналогично `e4`: `task11` («теряю ощущение себя») — ожидается `true`, `task3`
(«исчезновения меня как Личности») — `false`, при одинаковой конструкции.

**Практический вывод:** `task10` был пересмотрен (`e6` → `false`) — это сняло
противоречие и дало `e6` = 11/12. Оставшийся потолок — `e3` (2 ошибки в 0.05 от границы)
и `e9` (3 ложноположительных).

### 15.5 Внимание модели — не узкое место (доказано)
Внимание изолировано по строкам батча: 9 вопросов в батче дают идентичные
вероятности одному вопросу отдельно. Между вопросами нет интерференции,
которую можно разгрузить. Поэтому «разбить 9 вопросов на партии, чтобы
разгрузить внимание» **не может дать прироста точности** — только экономию
времени. Идея закрыта на собственных данных проекта.

### 15.6 Что это значит для дальнейшей работы
1. **Приоритет — второй независимый набор кейсов.** Пока его нет, любое число
   выше 90% нельзя объявлять: подгонка даст 234/234, а проверка покажет ~185.
   Узкое место измерений — размер выборки, а не модель.
2. **Fine-tuning** головы классификации — единственный путь, который авторы
   модели называют источником способности (README чекпоинта). Он требует
   десятки размеченных кейсов, то есть зависит от пункта 1.
3. **Низкорисковые улучшения, не требующие новых кейсов:** правка формулировок
   по одному элементу с замером (правило §13.3), и калибровка под приоритетные
   элементы вместо общей точности.

## 16. Фаза 4: разбор полюсов e3 — что оказалось важнее самих полюсов (02.10.2026)

### 16.1 Откуда взялась гипотеза: e7 доказывает, что модель умеет в 100%
`e7` даёт **26/26, AUC 1.000**. Значит 80% — не предел модели, а свойство наших
формулировок. Разница между идеальным и худшим элементом:

| | e7 (работает) | e3 (худший) |
|---|---|---|
| AUC | **1.000** | **0.592** |
| ошибок | 0 | 10 (из них 9 ложных) |
| вопрос | «Названа ли… эмоция?» — чистое присутствие | «Названо ли… **или только** текущая реакция?» — контраст |
| полюс `false` | «факты и ощущения тела» — **посторонний тип содержания** | «текущая эмоциональная реакция» — **тоже страдание** |

**Механизм (гипотеза, затем проверен замером):** модель — матчер тем (§4.5). Когда
оба полюса описывают страдание, эмбеддинги сходятся, и выбор невозможен: модель
тянет в «страдательнее». Отсюда перекос 34 FP против 11 FN.

### 16.2 Три гипотезы за один прогон
`e3_pole_experiment.yaml`, `tools/laya_pole_experiment.py`. Гипотезы разведены по
параметрам, иначе при любом выигрыше непонятно, что именно сработало:
**A base** — контроль; **B pure** — убран контраст из вопроса (полюс прежний);
**C ortho** — плюс ортогональный полюс в форме работающего e7;
**D nocr** — плюс полный отказ от критериев (§4.4, у нас не проверялось — §7).

Все 4 варианта идут **одним батчем** — внимание изолировано по строкам, поэтому
4 вопроса в одном прогоне дают те же вероятности, что и 4 отдельных вызова.
Весь эксперимент: **32 секунды**.

### 16.3 Результат: полюс двигает рабочую точку, а не различение
При фиксированном пороге 0.50:

| вариант | AUC | верно | FP | FN |
|---|---|---|---|---|
| A base | 0.592 | 16/26 | 9 | 1 |
| B pure | 0.580 | 16/26 | **6** | 4 |
| C ortho | 0.592 | 14/26 | **12** | **0** |
| D nocr | **0.657** | 15/26 | 8 | 3 |

AUC у A/B/C одинаковый — **форма полюса не улучшает различение**, она двигает
рабочую точку: FP 9 → 6 → 12. Значит вопрос «какой полюс правильный» был
неправильным; правильный вопрос — «где стоит порог».

При подобранном пороге (LOO-CV по кейсам):

| вариант | порог | верно | AUC | FP | FN |
|---|---|---|---|---|---|
| A base | 0.51 | 14/26 | 0.592 | 9 | 3 |
| C ortho | 0.67 | 16/26 | 0.592 | 7 | 3 |
| **D nocr** | **0.68** | **17/26** | **0.657** | **3** | 6 |

**Единственное, что дало прирост различения, — отказ от критериев:**
AUC 0.592 → **0.657**. Это независимое подтверждение абаляции авторов из §4.4
(`noul` без критериев 0.6667 против `noul` с критериями 0.4583) на наших данных.

Ложных срабатываний на приоритетном элементе: **9 → 3** (убрано 8, добавлено 2,
p = 0.109 — до p < 0.05 не дотягивает). Цена — рост пропусков 1 → 6.

### 16.4 Проверка на всех девяти элементах
`element_validation_rules_e3_nocr.yaml` — копия продакшна с изменённым **только** e3
(§13.3: правка пакетами противопоказана). Остальные восемь скопированы без правок.

| | база | кандидат | дельта |
|---|---|---|---|
| Всего | 189/234 | **190/234** | **+1** |
| e3 | 10 ошибок | **8** | −2 |
| e6 | 4 ошибки | 5 | **+1** |

Деталь настолько неожиданная, что потребовала отдельной проверки: **e6 не менялся
ни на символ, но его оценка ухудшилась.**

### 16.5 Побочная находка: правка одного элемента сдвигает остальные
`test/laya_probe/cross_element_leak.py` сравнивает вероятности двух прогонов покейсно:

| элемент | средний сдвиг p | максимальный | перевёрнутых вердиктов |
|---|---|---|---|
| e3 (правился) | 0.18527 | 0.55855 | 18 |
| **e6 (не правился)** | **0.00909** | **0.03830** | **1** |
| e1, e2, e4, e5, e7, e8, e9 | 0.00000 | 0.00000 | 0 |

`task3`, e6: p **0.357 → 0.369** при пороге **0.36**. Вердикт перевернулся.

**Механизм:** вопросы логически независимы (внимание изолировано по строкам, §15.5),
но батч считается одним матричным умножением, и его внутренняя разбивка зависит от
общей формы `[batch, seq_len]`. Укоротив вопрос e3, мы сдвинули `max_seq_len`,
изменили паддинг — и вместе с ним float-ошибки остальных строк. Документация
предупреждала об этом лишь вскользь (§7, «смена формы батча слегка меняет float»).

**Следствие, обязательное для всех дальнейших замеров:** разница в 1–2 ошибки на
элемент нельзя приписывать самому изменению. Это отдельный источник шума ПОВЕРХ
шума выборки (§15.4). Каждый элемент надо либо считать в собственном батче, либо
закладывать ±1 ошибку как погрешность.

Побочно вскрылась хрупкость калибровки: `task3` по e6 держится на пороге 0.36 с
запасом 0.003 — такой порог нельзя считать откалиброванным.

### 16.6 Вердикт по Фазе 4
- Три гипотезы проверены, **ни одна не дала статистически значимого выигрыша**
  (p ≥ 0.109 на всех).
- Реальный и воспроизводимый эффект: **отказ от критериев на e3** поднимает AUC
  элемента 0.592 → 0.657 и срезает ложные срабатывания 9 → 3.
- Общий счёт 189 → 190 при стоимости одного случайного переворота в e6 (float).
  **Чистый эффект изменения, без этого артефакта, — +2 на e3, что в пределах шума.**
- Гипотеза «форма полюса управляет разделением» — **опровергнута**: A/B/C дали
  одинаковый AUC. Управляет она рабочей точкой, а различение улучшает только
  отказ от критериев.
