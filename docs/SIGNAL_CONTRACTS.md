# Контракты сигналов `emit_signal` (SSOT + правило генерации)

> **Критическое правило (нарушение = баг «тихо упал, в чат никто не ответил»):**
> **Сигнальный агент ОБЯЗАН генерировать ответ под грамматикой/JSON-schema своего
> контракта. Никогда не отключай грамматику для сигнальных агентов и не добавляй
> `default`-ветку в маршрутизатор как «защиту» — это костыль, маскирующий корень.**

## Что такое контракт сигнала

Единый источник правды (SSOT) — `agents/<команда>/signals/root.schema.json`:

```json
{ "agents": { "<agent_id>": { "key": "<сигнальный key>", "value": { "<JSON Schema value>" } } } }
```

Агент вызывает `emit_signal` как инструмент **внутри своего ответа**. Конверт:

```json
{ "tool": "emit_signal", "arguments": { "key": "<key>", "value": { ... } } }
```

- Свободные рассуждения агента живут в **think-блоке** гибридной GBNF
  (`verdict_contract`-стиль, Method 3) и попадают в сессию как `thought`-сообщения —
  в конверте поля `thought` НЕТ.
- `arguments.value` — **защищённая структура** по схеме контракта (имена полей, `enum`,
  `const`, `required`, `additionalProperties:false`).

## Разделение размышлений и структуры (один запрос)

Двухфазный режим (Phase 1 свободные размышления → Phase 2 JSON) удалён 17.10.2026
(см. `tasks/17.10.26 Удаление двухфазного режима.md`). Теперь всё происходит в одном
запросе:

1. **Hybrid GBNF** (`build_signal_envelope_grammar`) — грамматика
   `think-block envelope-json`: модель размышляет в `</think>`-блоке (лимит
   `think_budget_chars` из грамматики), потом выдаёт строгий конверт.
2. **Автономный Phase-2 JSON-only retry** (`build_signal_envelope_json_only_grammar`,
   `orchestrator/mod.rs` «Phase 2: JSON-only fallback») — если за ход сигнал не был
   доставлен, оркестратор делает единственный повторный вызов уже БЕЗ think-блока
   (`enable_thinking=false`), под грамматикой только envelope-json.

Поэтому поле `thought` внутри конверта не нужно: рассуждения живут в think-блоке
отдельного канала. Грамматика ограничивает **только форму** сигнала (имена/типы/допустимые
значения полей). Это тот же паттерн, что OpenAI `tool_calls` / llama.cpp `json_schema`.

llama.cpp на лету компилирует JSON Schema (Draft 7) в GBNF (модуль
`common/json-schema-to-grammar.cpp`), маскируя на каждом шаге недопустимые токены.
Результат: модель **физически не может** выдать не то имя поля и не то значение (не из
`enum`). Источник: официальный README llama.cpp (`--json-schema`), DeepWiki «Grammar
and Structured Output», и устоявшаяся практика constrained decoding (гарантирует 100%
валидный вывод, тогда как «просто попроси в промпте JSON» падает 5–15% времени).

## Как это проводится в коде (НЕ ломать)

- `domain/signals.rs`:
  - `load_signal_contract()` — грузит контракт агента из `root.schema.json`.
  - `build_signal_envelope_schema()` — собирает строгую JSON-schema **обёртки**
    `emit_signal` из контракта (с `additionalProperties:false`, `const` ключей,
    `required`). Без `$ref` (сломаны в llama.cpp, #8073).
  - `validate_signal_value()` — честная валидация `value` против обязательных полей
    контракта. Возвращает явную ошибку на retry, если форма искажена.
- `domain/orchestrator/mod.rs` (`run_agent_node`):
  - Для сигнального агента (есть контракт) ставится
    `engine.set_grammar(GrammarSpec { gbnf: Some(build_signal_envelope_grammar(contract)) })`.
    Метод строит hybrid GBNF: `think-block envelope-json` (Method 3 из `docs/gbnf.md`).
    `disable_reasoning` НЕ включается — модель думает в `<think>`.
    Ветка `else { None }` для сигнальных агентов **удалена** — отключать грамматику
    запрещено.
- `domain/orchestrator/dispatch.rs` (`execute_tool_call`, ветка `emit_signal`):
  - если `value` не прошёл `validate_signal_value()` — возвращается явная ошибка модели
    на retry (честно, не тихо).
- `domain/signals.rs` (`build_cloud_signal_prompt_block`, 03.11.26):
  - рендерит контракт в текстовый блок `[ТРЕБОВАНИЕ СИГНАЛА (CLOUD MODEL)]` для облачных
    движков: слотовый контракт → слотовая инструкция (якоря `Element N: `, вердикты
    `"eN": true|false`, trailing-слоты); обычный → конверт с реальным key и описанием
    value-схемы (`describe_value_schema`, включая `description` значений). Вставку в
    системный промпт делает `prompt.rs` (6-й параметр `build_system_prompt` —
    `signal_contract: Option<&SignalContract>`). Локально механику принуждает грамматика —
    промптовый дубль в .md агентов не нужен.

## Разбор бага (кейс: модель исказила имя поля сигнала)

**Симптом:** в чат никто не ответил, лог обрывается на `signal_router → нет target`,
движок остановлен.

**Корень:** оркестратор ставил сигнальным агентам `set_grammar(None)`, поэтому модель
генерировала **без ограничения** и выдала неправильное имя поля (напр. `status` вместо
`e1`). `signal_router` читает нужное поле → не находит → `target: None` → граф
завершается, ни один `message`-узел не выполняется → в `ctx.messages`
не добавляется ни одного `message` → workflow-режим возвращает пустоту.

**Почему `default`-ветка — костыль (не делать):** это маскирует корень (модель отпустили
без грамматики) и зашывает «безопасное» поведение, которое может быть неверным. Правильно
— **запретить искажение формы на этапе генерации** (грамматика), а если оно всё же
проскочит, **честно вернуть ошибку** (`validate_signal_value`), а не молча маршрутизировать
в обход.

## Правило развода: фронтенд-агент vs signal-контракт (17.10.26)

1. **Signal-контракт даётся ТОЛЬКО агенту, чей `key` реально потребляется** —
   `signal_router.signal_name`, condition field-путь (`key` / `key.<sub>`),
   `cases_priority` или шаблоном `{{ signals.<key> }}` в графе, который его
   вызывает: контракт ни с одним потребителем = мёртвый сигнал (работа
   выбрасывается, ответ в чат не попадает).
2. **Фронтенд-агент, обязанный писать отчёт пользователю, и signal-контракт
   несовместимы.** Method 3 оформляет ответ конвертом `emit_signal` — при
   `output_type: message` на выходе оказывается пустое сообщение (кейс
   `synthesizer` 17.10.26: контракт `destructor_type` без консьюмера, пустой
   msg_5 в `sessions/1792249465685.json`). Оставила frontmatter-запись
   `tools: [emit_signal]` — значит агент НЕ фронтенд-агент, и наоборот.
3. **Диагностика**: `workflow_engine/signal_consumer_check.rs` → код
   `SIGNAL_CONTRACT_UNCONSUMED` — `GraphDiagnostic` в
   `editor_fidelity::analyze_workflow_fidelity` и `log::error!` при
   `load_workflows` (одной строкой, агрегированно). Если она сработала —
   чинить корень (убрать контракт или добавить потребителя), а не порог.

## Доставка think-тел сигнальных агентов (инцидент 01.11.26)

**Симптом:** в отчётах страницы тестов у слотового валидатора (Вариант B,
`validator.md`) `reasoning_full` пуст при том, что модели реально пишут тела
слотов. В чате у сигнальных агентов не видно ни одной мысли «(размышление)».

**Корень (доказан по боевому логу 01.11.26):** сигнальный агент завершает
итерацию через `DispatchCtl::Break` (`handle_emit_signal` → `dispatch.rs`,
`return Ok(DispatchCtl::Break)`; то же для native-tools сигналов —
`execute_native_tool_calls`). Диспатч-матч (`Break => break`) выходит из цикла
`run_agent_node` **раньше** thought-блока, поэтому `extract_think_content`
для сигнальных агентов никогда не доходил до пуша: `phase1_thinking` не
выставлялся, `SubCall.thinking` = None, thought-сообщений нет. Движок и плагин
не виноваты: при `disable_reasoning=true` модели пишут think-теги литерально в
`content`, тела лежат в сыром ответе (3235 симв. в логе), reasoning-канал пуст
(«+0 думателя»).

**Фикс (НЕ ломать):**
1. `run_agent_node`: тела think-блоков извлекаются **до** dispatch-веток
   (`last_think_bodies`, покрывает любой выход из итерации — Break legacy-конверта,
   native-tools Break, текстовый финал) и допушиваются **после** цикла, перед
   созданием `SubCall` (флаг `bodies_pushed` не даёт задвоения для текстовых
   финалов, у которых пуш сделал thought-блок внутри цикла).
2. Маппинг `reasoning_full` в отчётах (`api/test.rs`, `domain/pipeline_test.rs`)
   берёт reasoning из `sub_calls` **самого сообщения** (приоритет), фолбэк — карта
   по `author`. Сверка «карта SubCall по author» не работает: `SubCall.agent_name`
   хранит display-name («Валидатор данных»), а `ChatMessage.author` — id агента
   (`validator`); ключи не совпадают (пустой канал 01.11.26).
3. Анти-дублирование: thought-сообщение, чьё `content` само является частью
   reasoning (тело слота), `reasoning_full` не получает — канал несёт
   сообщение-результат (анализ ноды).

**Проверка:** 616/0 юнит-тестов; отчёт `custom_report_2026-11-01_08-01-43` —
`reasoning_full` заполнен, в md рендерятся блоки «Размышления», у валидатора 9
thought-сообщений с телами слотов.

## Взаимодействие think-капа с деградацией слотов (доказано 01.11.26)

`auto_think_budget_chars` (`domain/signals.rs`) делит think-бюджет на число
drafts: для 9-слотового валидатора ≈ 332 символа/слот. Последствия,
измеренные на батчах 01.11.26 (отчёты `custom_report_2026-11-01_07-47-00` —
verified_1_libido_block_spasms, `custom_report_2026-11-01_08-01-43` —
somatic_throat_fever):

- Модели, умещающие разбор в кап (Ornith 105–287 симв., NeoHorse), дают тела
  «цитата → evidence_test → must_not_be → Вердикт» — вердикты заземлены.
- Деградировавшие модели (LFM2.5) сжигают бюджет на вступлении-сводке: **все 9
  тел ровно 331 символ**, обрезаны на полуслове, вердикт выносится без
  завершённого разбора; на соматическом кейсе — конфабуляция
  («психосоматические метафоры» из чисто телесной жалобы) на английском.
- Qwen3.8: тела полные и с дословными цитатами, но граница соматика/ментал
  (Шаг 0) применяется неверно («гудит» → ментал, «болит горло» → триггер) —
  эпистемический слой, капой не лечится.
- «Весь-true»/«весь-false» флипы между прогонами — следствие: при
  деградировавшем/обрезанном теле булев токен выбирается по приоре модели.
  Кластер «весь-true» в двух прогонах 01.11.26 не воспроизвёлся.

## Профстандарты классификаторов (policy-in-prompt) и следствия

Подтверждено источниками (проверено 01.11.26):

- **Llama Guard 3 (Meta)** — таксономия категорий встраивается в промпт
  (размеченные секции `<BEGIN UNSAFE CONTENT CATEGORIES>`), few-shot примеры в
  контексте, вывод = вердикт + код категории; кастомизация политики без
  переобучения. [Model Card](https://huggingface.co/meta-llama/Llama-Guard-3-8B),
  [статья Llama Guard](https://arxiv.org/html/2312.06674v1).
- **ShieldGemma (Google)** — политика в промпте, спроектирована под zero/few-shot,
  вывод safe/unsafe. [Документация](https://ai.google.dev/gemma/docs/shieldgemma).
- **Policy-as-Prompt (2025)** — LLM чувствительна к структуре/форматированию
  политики в промпте; конверсия политики в промпт — ключевая задача.

Архитектура валидатора (e1..e9 = таксономия в промпте, структурный вывод
слотовыми грамматиками) совпадает со стандартом. Следствия в порядке §00.2
(конструктивное → параметр):

1. **Quote-first с механической проверкой** (конструктивно): каждый вердикт
   слота обязан иметь непустое тело-доказательство (мысль слота); true-вердикт —
   дополнительно дословный фрагмент жалобы (span ≥ 4 слов); проверка
   (`quote_gate.rs`, `check_grounding`) **до** принятия вердикта; пустое тело
   или незаземлённый true → слот структурно невалиден → ретрай/флаг. Ловит
   класс LFM2.5 (конфабуляция без разбора и дословных цитат). Честная пометка:
   в найденных источниках напрямую не описана — конструктивное предложение
   проекта; класс Qwen3.8 (верная цитата, неверная классификация) не ловит.
2. **Generic few-shot по элементам** (форма запроса): синтетические примеры
   границы соматика/ментал в промпте — общий принцип, не кейсы юзеров
   (совпадает с запретом хардкода в AGENTS.md §«Запрет хардкода конкретных
   кейсов»). Ловит часть класса Qwen3.8.
3. **Self-consistency** (k сэмплов + большинство) — параметр, k× стоимость,
   в последнюю очередь.

## Чек-лист при добавлении нового сигнального агента

1. Добавить запись в `signals/root.schema.json` (`key` + `value`-схема, обязательные поля
   в `required`, `additionalProperties:false`).
2. Убедиться, что `build_signal_envelope_schema` покрывает схему (без `$ref`).
3. В графе `signal_router` читает ровно те поля, что в контракте (SSOT — не дублировать
   строковые литералы полей в YAML, если можно вывести из контракта).
4. НЕ добавлять `default` к `signal_router` «на всякий случай».
5. **Проверить потребителя**: в графе, который вызывает агента, его ключ
   должен реально читаться (`signal_router` / condition-путь / шаблон).
   Диагностика `SIGNAL_CONTRACT_UNCONSUMED` при загрузке графа — сигнал
   «чинить раньше, чем запускать».
6. Запустить тесты `domain/signals.rs` (`validate_signal_value_*`, `envelope_schema_*`)
   и `workflow_engine/signal_consumer_check` (`dead_contract_*`, `production_graph_*`).
