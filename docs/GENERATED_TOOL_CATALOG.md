## Built-in инструменты (код)

- `todo_write` — Управление чек-листом задач агента. Используй для многошаговых задач, чтобы не терять план (он переживает сжатие контекста). Действия: add (нужен title), done/remove (по index или title), clear (очистить), list (показать).
- `todo_list` — Показать текущий чек-лист задач агента (что сделано, что осталось).
- `emit_signal` — Сохранить сигнал/маркер в сессию. Другие агенты, экстрактор и phase_router увидят его. Принимает key (имя сигнала) и value (произвольный JSON-объект с данными).
- `read_spill` — Дочитать полный результат большого инструмента, сохранённый в файл spills (локатор приходит в сообщении '[РЕЗУЛЬТАТ ИНСТРУМЕНТА сохранён в файл spills]'). Принимает path (путь к spill-файлу); offset — 1-based позиция в символах (по умолчанию 1); limit — сколько символов прочитать (по умолчанию 16000, максимум 16000). Артефакт может быть большим — дочитывай ДИАПАЗОНАМИ по подсказкам 'Продолжай с offset=N', не копируй целиком.

## Инструменты агентов (TS, нода `tool` — agents/<agent>/tools/)

- `_shared/tools/read_md_section.ts` (агент `_shared`) — read_md_section — ОБЩИЙ тул команд агентов: читает секцию markdown-файла по заголовку. Живёт в `agents/_shared/tools/` — вне бизнес-логики команд, чтобы любую команда могла дёрнуть его из графа нодой `custom_tool_call` (tool_file: ../../_shared/tools/read_md_section.ts). Вход: Deno.args[0] = JSON (значения приходят СТРОКАМИ от движка): {"file": "<путь от корня agents/>", "heading": "## 2"} Выход: ТОЛЬКО JSON в stdout: {"file": "...", "heading": "...", "content": "<текст секции>"} Секция — от строки заголовка до следующего заголовка H1/H2 или конца файла. Корень agents/ выводится из import.meta.url, НЕ из CWD процесса: у one-shot Deno он не обязан совпадать с папкой приложения. Честные отказы (stderr + exit(1), движок превращает их в ошибку ноды): не-JSON вход, файл вне agents/, файл не найден, секция не найдена, секция пуста. Никаких нечётких фолбэков: тихо отдать «похожую» секцию — значит отдать агенту лечение не по его паттерну.
- `astrologist/tools/ayanamsa.ts` (агент `astrologist`) — Айанамша Sri Surya Siddhanta (эквивалент SE_SIDM_SURYASIDDHANTA из Swiss Ephemeris) + долгосрочная прецессия Vondrák/Capitaine/Wallace 2011. Источники: - J. Vondrák, N. Capitaine, P. Wallace, "New precession expressions, valid for long time intervals", A&A 534, A22 (2011) — полиномы и периодические члены прецессии/наклонности (опубликованные данные); - константы эпохи айанамши {t0 = 1903396.8128654 (UT), ayan_t0 = 0} — фактическое определение режима SE_SIDM_SURYASIDDHANTA (Swiss Ephemeris): мессой вход среднего Солнца в Овен в точке среднего равноденствия 21.03.499, Уджайн (75.7684565 E), 7:30:31.57 UT; - алгоритм айанамши повторяет семантику swi_get_ayanamsa_ex (без SE_SIDBIT_ECL_DATE): точка весеннего равноденствия даты прецессируется к эпохе t0, её эклиптическая долгота на эпохе t0, взятая с обратным знаком, и есть айанамша. Внутренняя проверка замыкания: ayanamsa(t0) === 0 по построению.
- `astrologist/tools/build_knowledge.ts` (агент `astrologist`) — build_knowledge — сборка «досье» из базы знаний под конкретную карту и вопрос. Вход: один argv-токен — плоский JSON строк вида {"lagna": "<вывод calc_chart.output.lagna>", "planets": "<...output.planets>", "topic": "<...output.question_topic>", "transits": "<...output.transits>"} Движок сериализует не-строки в JSON-строку (как у tarot lookup), поэтому поля принимаются и строкой-JSON, и готовым объектом/массивом. Читает ../database/ относительно файла тула (import.meta.url) — прецедент lookup_tarot_cards.ts; allow-read Deno покрывает папку команды (custom_tool.rs). Выход ТОЛЬКО JSON в stdout: {"text": "...", "files_used": [...], "sections": N} Состав досье: - файл лагны; - все 12 связок «управитель дома в доме» этой карты (7 грах-управителей, Раху/Кету владений не имеют); - йоги, детектированные в карте (vedastro_detect.ts) — только они, секции из yogas.md; недетектированные йоги в досье не попадают (00.2); - гочара: ровно по одной транзитной секции на граху (дома от Луны), из gochara.md; - правила периодов даш: универсальные + солнечные по состоянию Солнца, из dasha_rules.md; - файл темы вопроса (неизвестная/пустая тема → general). Любая недостающая часть БЗ, битый вход или детектированный id без секции в базе — stderr + exit 1: честный отказ, workflow останавливается, тихой деградации нет.
- `astrologist/tools/calc_chart.ts` (агент `astrologist`) — Расчёт ведической натальной карты из файла .jhd + текущие транзиты. Контракт тулов графа (как у tarot-master): один argv-токен — плоский JSON строк `{"jhd_path": "..."}`; на stdout — ТОЛЬКО JSON-объект; любая ошибка — сообщение в stderr + exit 1 (честный отказ, workflow останавливается). Астрономия: astronomy-engine (вендор в ./vendor, VSOP87). Система расчёта (планетная модель, айанамша, год даши) выбирается ОДНОЙ строкой в vedic_system.ts (VEDIC_SYSTEM; дефолт "drik": Drik + Lahiri + 365.2425). - `astrologist/tools/chart_analysis.ts` (агент `astrologist`) — Аналитический слой джйотиш поверх позиций грах: функциональные управители домов (от лагны), граха-дришти (включая спец-аспекты Марса/Юпитера/Сатурна), достоинства (exaltation/moolatrikona/own/debilitation), сожжение, варготтама и чаракараки (Джаймини). Назначение — предрасчёт ДО отправки в LLM (см. AGENTS.md, правило 00.2): модель не обязана помнить, какими домами владеет планета для конкретной лагны и куда падают спец-аспекты. Все функции чистые и детерминированные, эфемерид не касаются — тестируются на фиксированных числах. Источники таблиц (классическая доктрина Парашары, BPHS): - владения знаками, экзальтация/падение, муллатрикона (градусные диапазоны), - дришти: все грахи смотрят в 7-й дом от себя; Марс — 4/7/8, Юпитер — 5/7/9, Сатурн — 3/7/10 (спец-аспекты ЗАМЕЩАЮТ общий 7-й, не добавляются к нему); - орбисы сожжения: Луна 12°, Марс 17°, Меркурий 14° (ретро 12°), Юпитер 11°, Венера 10° (ретро 8°), Сатурн 15° — расстояние по долготе до Солнца. Раху/Кету: владений и достоинств не имеют (школы расходятся — честный null, а не выбранное мнение); сожжение узлов не определяется.

- `astrologist/tools/vedic_system.ts` (агент `astrologist`) — ЕДИНСТВЕННЫЙ переключатель ведической системы расчёта астролога. Система меняется ОДНОЙ строкой — значением VEDIC_SYSTEM ниже. "sss" — Sri Surya Siddhanta (традиционная школа): • планетная модель: Сурья-сиддханта (эпициклы, мандоччи/шигроччи) — ЕЩЁ НЕ РЕАЛИЗОВАНА, тул честно откажется (см. calc_chart.ts); • айанамша: Sri Surya Siddhanta — SE_SIDM_SURYASIDDHANTA; • год даши: «Year with 360 tithis» (354.3670680 сут). Константы Lahiri/SS — из исходников Swiss Ephemeris (sweph.h, таблица ayanamsa[]): JHora построена на Swiss Ephemeris, поэтому Lahiri в туле и в JHora совпадает на уровне модели прецессии (проверяется гейтом).

Секции берутся из `psychotherapist/database/inner_9_patterns_by_gifts.md` (файл приходит аргументом — граф знает раскладку базы), где `## N` = больной тип N + его лечение (Дыра 3, Идол 9, Дар лечебного типа по Безопасности, механика, формула сдвига). Соответствие этаж → паттерн (лечение e4/e8/e9, решение владельца 06.11.2026): Этаж 0  (элементы 1, 4, 7) → floor0_type из сигнала валидатора Этаж -1 (элементы 2, 5, 8) → floor1_type из сигнала валидатора Этаж -2 (ядро, элементы 3, 6, 9) → core (floor2_type, вычислен нодой compute_pattern по SAFETY-сцепке) Вход: Deno.args[0] = JSON (значения приходят СТРОКАМИ от движка): { "report": "<JSON-строка сигнала validator_report или сам объект>", "core":   "<цифра 1..9 из {{ nodes.compute_pattern.output.floor2_type }}>" } Выход: ТОЛЬКО JSON в stdout: {"content": "<трёхэтажный блок с подписями>", "floor0": "…", "floor1": "…", "core": "…"} Честные отказы (stderr + exit(1), движок превращает их в ошибку ноды): не-JSON вход, report не объект, этажи/ядро не цифры 1..9, файл вне agents/, файл не найден, секция не найдена. Никаких нечётких фолбэков: тихо отдать «похожую» секцию — значит лечить не тем паттерном.

- `tarot-master/tools/draw_card_numbers.ts` (агент `tarot-master`) — draw_card_numbers — RNG-тул команды «Таролог». Вход: Deno.args[0] = JSON {"count": "3"} (значения приходят СТРОКАМИ от движка). Выход: ТОЛЬКО JSON в stdout: {"count": N, "numbers": [N уникальных 0..77], "orientations": ["upright"|"reversed", ...]} Ориентация каждой карты — часть случайного расклада (традиция RWS): её решает этот тул, а не LLM. Файлов не читает (переносимая механика). Любая невалидность входа — сообщение в stderr и exit(1): движок превращает ненулевой exit в честную ошибку ноды.
- `tarot-master/tools/lookup_tarot_cards.ts` (агент `tarot-master`) — lookup_tarot_cards — лукап-тул команды «Таролог». Вход: Deno.args[0] = JSON {"numbers": "[3,21,57]", "orientations": "[\"upright\",...]"}. ВАЖНО: движок резолвит не-строку как JSON-массив, сериализованный в строку, поэтому оба поля нормализуются одинаково: принимается и строка-JSON-массив (JSON.parse), и настоящий массив. Читает ../database/cards.json относительно файла тула (путь от import.meta.url, абсолютные пути не хардкодятся). cards.json — SSOT карт, список дублировать запрещено. Выход ТОЛЬКО JSON в stdout: {"count": N, "positions": [...], "cards": [{...поля карты..., "orientation": "upright"|"reversed"}]} Позиции — константа бизнес-логики тула (не движка): count=1 → ["совет"], count=3 → ["прошлое", "настоящее", "перспектива"]. Любая невалидность — stderr + exit(1) (движок превращает в ошибку ноды).
