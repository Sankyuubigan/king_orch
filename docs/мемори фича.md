## 1. Зачем (проблема)

подбирать. Промпт-костыли без факта не спасут (спец, Q5): в промпте должен лежать сам факт.

**Прецедент (21.11.2026, сессия психотерапевта):** модель путала пол юзера, хотя он явно писал
«я мужчина». Полная цепочка причин разобрана в
`tasks/261121_0809-15f458c9/Отчёт специалисту — пол и твоеmu.md`:

1. **Корневая механика (ИСПРАВЛЕНА 21.11)** — компакция контекста удаляла сообщение юзера
   «я мужчина» в каждом ходу (бюджет считался от мёртвого слота 16384 вместо железного потолка;
   регрессия от тир-слота `6f2bf21` + плагинный PRP `1df75d6`). Фрейм агента тоже срезался.
   Без якоря модель воблила и зеркалила собственные feminine-ответы ранних ходов.
2. **Остаточный риск (для ЭТОЙ фичи)** — даже после исправления честная компакция под железо
   на очень длинных сессиях всё равно может срезать старые факты из истории (правило
   «не удалять только последнюю реальную реплику»). Факты, заявленные в начале долгого диалога,
   структурно несгораемыми не являются. Несгораемость даёт только **pinned-персона**.

## 4. Чего не хватает — «писатель фактов»

**Писатель — это механизм, который ЗАПИСЫВАЕТ факт, когда юзер его заявляет в чате**
(«я мужчина», «меня зовут …», «я левша»), в постоянное хранилище, откуда персона собирается
при сборке каждого хода.

- **В коде его НЕТ** (rg-проверка 21.11.2026: механизма персоны/досье в `src-tauri` нет —
  ни писателя, ни хранилища).
- Ближайший существующий механизм — факт-экстрактор графа
  (`workflow_engine/fact_extractor.rs`): он возвращает JSON `{"fact_id": true/false}` — это
  **булевы флаги маршрутизации одного хода**, они нигде не сохраняются между ходами и не
  годятся как хранилище фактов.
- Строить читалку (preamble-инжект) без писалки = мёртвый код → правило §0.7
  (прецедент `report_validator_silent` 09.11.2026 — построили ноду, ветка недостижима, откат).

## 5. Дизайн-варианты (выбирает владелец)

- **A. Минимальный (sidecar сессии).** Факт-экстрактор (или дешёвая проверка на прохождении)
  при заявлении факта пишет его в per-session sidecar-файл; оркестратор при сборке хода
  инжектит однострочную персона-строку как pinned-сообщение.
  *Плюс:* без правки графов. *Минус:* хранение per-session, нет единого каталога.
- **B. Графовый (полный).** Нода-писатель (backend, после signal-роутинга) +
  хранилище `<KingOrchData>/personas/<session>.md` (или `app_data/sessions`).
  *Плюс:* SSOT-паттерн, видно в логах, легко расширять (имя/рука/возраст…).
  *Минус:* правки всех прод-графов, новый узел в каждом.
- **C. Отложить (рекомендация AI от 21.11, владелец 22.11 выбрал «делаем позже»).**
  Сначала прогрев боевой сборкой после фаз 1–3: корневая причина (резка якоря) исправлена,
  самоподдержка feminine-зеркала могла быть чистым следствием потери якоря. Замер покажет,
  нужен ли механизм вообще. *Запасной путь — A.*

## 6. Технические требования (когда возьмём в работу)

1. **Честность фактов (§00.3):** хранить ТОЛЬКО то, что юзер заявил явно. Пол из имени/фото/
   стиля речи не выводится никогда. Неизвестный факт = отсутствует (не «угаданный дефолт»).
2. **Семантика обновления:** коррекция («нет, я женщина») → UPDATE существующего факта,
   не append дубля. Дедуп обязателен.
3. **Инжект:** pinned-сообщение в контексте КАЖДОГО `llm_worker` графа (как авто-история),
   позиция 1 (рядом с фреймом агента), wording из ЕДИНОГО шаблона (SSOT текста preamble).
4. **Данные персоны не проходят через думателя** при сборке — конкатенация хранимых фактов,
   детерминированная (LLM участвует только в ИЗВЛЕЧЕНИИ факта из реплики, если взяли вариант A/B).
5. **Гейт верификации (зафиксировать ДО реализации):** длинная сессия (20+ ходов), на ходу 1
   юзер заявляет «я мужчина» → все ответы держат мужской род; компакция в середине сессии
   НЕ удаляет персона-строку (проверка по prompt_log, что pinned жив во всех вызовах).
6. **Компактность:** блок ≤ 20 токенов; список фактов ограничен (пол, имя, ведущая рука —
   базовый набор; расширение — отдельное решение).
